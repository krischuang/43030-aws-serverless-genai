# Local Evaluation Report

Everything in this report was produced **without a real AWS account, without any real
Amazon Bedrock inference call, and without AWS credentials of any kind**. Two independent
local mechanisms were used, combined to cover more ground than either alone:

1. **`npm run evaluate:mock`** — the project's existing 13-case evaluation harness
   (`evaluation/`), run in mock mode (`evaluation/transports.ts`'s `MockTransport`, which
   runs the real handler code with the Bedrock/DynamoDB SDK clients stubbed in-memory).
2. **`npm run test:local`** — the new local integration/security suite
   (`test/local-integration.test.ts`, `test/local-security.test.ts`), run against a real
   local `amazon/dynamodb-local` Docker container with Bedrock routed through the
   existing `MOCK_BEDROCK`/`aws-sdk-client-mock` seams.

Raw output for both is reproduced below, unedited. No dimension is reported as `pass`
unless it was actually exercised in one of these two ways.

## 4. Explicit Limitations

Stated plainly, consistent with this project's own existing practice (`docs/evidence-guide.md` rule 4: "do not manufacture evidence"):

- No real Bedrock model was ever invoked. "Safety Behaviour" above means this
  application's own validation/flagging logic, not the real Bedrock Guardrail's
  decision.
- Mock-mode latency figures (0–7ms) are an artefact of an in-process stub, not a
  latency measurement of anything resembling production behaviour. They are not
  presented as such anywhere in this repository.
- DynamoDB Local is a real DynamoDB-API-compatible engine, not a byte-for-byte clone of
  production DynamoDB — it does not meter capacity, and some advanced features
  (DAX, Global Tables, some IAM-condition-based access patterns) do not apply to it at
  all. For this project's schema (one table, no GSIs, no IAM conditions on item access)
  that gap is immaterial, but it is worth stating rather than assuming away.
- Groundedness remains unimplemented in the evaluation harness itself (a code-level gap,
  not a deployment gap) — see `docs/uts-a3-goal4-evidence.md` for the full discussion of
  why, and why it was not added as a cosmetic check in this review.

## 5. What Changed Relative to the Mock-Only Baseline

Before this review, "mock evaluated" meant exclusively "mocked Bedrock + mocked
DynamoDB" (the existing 155 tests, `aws-sdk-client-mock` throughout). This review adds a
second, independent local verification layer — real DynamoDB Local — for exactly the
claims that a fully-mocked DynamoDB client cannot actually prove: that the real
`PutCommand`/`GetCommand` wire calls, the real `ConditionExpression`, and the real error
types (`ResourceNotFoundException`) behave the way the application code assumes. Nothing
in this report upgrades any claim to "deployed" or "live" — those terms are reserved
for a real AWS account, which this review never touched (see
`docs/deployment-readiness.md`).
